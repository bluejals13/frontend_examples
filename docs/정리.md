# [기술 분석 리포트] 웹 아키텍처 API 통신 레이어 및 렌더링 성능 비교 분석

**문서 개요**
동일한 백엔드(Spring Boot + MariaDB) 환경에서 도서 관리 시스템(CRUD)을 구축하고, 프론트엔드 아키텍처 방식에 따른 네트워크 통신 비용과 서버 구조적 차이를 F12 트레이싱 데이터를 통해 비교 분석한 결과입니다.

---

## 1. 아키텍처 구성 모델

* **모델 A (현대적 SPA):** React 기반 Client-Side Rendering (CSR). 브라우저가 백엔드 API를 **직접 호출 (1-Hop)**.
* **모델 B (전통적 프록시):** PHP + jQuery. 브라우저가 PHP를 호출하고, PHP가 내부 cURL을 통해 백엔드를 호출 후 반환하는 **프록시 구조 (2-Hop)**.

---

## 2. 수치적 성능 비교 (Network Latency)

단일 데이터(`ID: 7`) 조회 시 발생하는 네트워크 Hop(단계)에 따른 지연 시간 측정 결과입니다.

| 지표 | 모델 A (React 직접 통신) | 모델 B (PHP 프록시 통신) | 측정 결과 요약 |
| --- | --- | --- | --- |
| **API 통신 구조** | Browser ➔ Spring Boot | Browser ➔ PHP ➔ Spring Boot | 1-Hop vs 2-Hop |
| **응답 소요 시간** | **16 ms** | **57 ms** | 모델 A가 **약 3.5배(71%) 더 빠름** |
| **병목 발생 구간** | 없음 | PHP cURL 연결 및 핸들링 | 중간 레이어(웹 서버)의 처리 오버헤드 |

---

## 3. 프록시 레이어(2-Hop) 구조가 야기하는 3대 잠재적 리스크

단순한 속도 차이(16ms vs 57ms)를 넘어, 서비스 규모가 확장될 때 모델 B(프록시 방식)가 마주하게 되는 근본적인 아키텍처 한계점입니다.

### ① 동시 접속자 처리량 저하 (Thread Starvation)

* **문제:** PHP는 Spring Boot의 응답이 완료될 때까지 자신의 서버 스레드(Socket)를 점유한 상태로 대기합니다.
* **실무 영향:** 대규모 트래픽 발생 시, 웹 서버(PHP/Nginx)의 가용 스레드가 순식간에 고갈되어 **서버 동시 접속 처리량(Concurrency)이 급감**합니다. 반면 React 방식은 서버를 거치지 않으므로 웹 서버의 스레드를 낭비하지 않습니다.

### ② 불필요한 데이터 가공 오버헤드 (Parsing Overhead)

* **문제:** 백엔드가 내려준 JSON 데이터를 브라우저에 전달하기 위해 불필요한 직렬화/역직렬화가 반복됩니다.
* **실무 영향:** [Spring Boot(JSON) ➔ PHP(CURL 문자열 수신 ➔ 배열 파싱 ➔ 다시 JSON 변환) ➔ Browser]의 단계를 거치며 **웹 서버의 CPU 및 메모리 연산 비용이 2중으로 낭비**됩니다. React는 백엔드 데이터를 브라우저 엔진이 직접 파싱하므로 중간 서버 연산 비용이 0%입니다.

### ③ 연쇄 장애 위험 (Cascading Failure)

* **문제:** 백엔드(Spring Boot)에 병목이나 지연이 발생할 경우, 장애가 웹 서버(PHP)까지 전이됩니다.
* **실무 영향:** 모델 A는 백엔드 장애 시 해당 API를 호출한 화면 영역만 실패하는 단일 장애점(Fault Isolation)으로 방어가 가능합니다. 하지만 모델 B는 대기 중인 요청들이 웹 서버를 마비시켜, API와 무관한 **정적 페이지들까지 모두 다운되는 연쇄 장애**를 일으킵니다.

---

## 4. 최종 결론 및 시사점

1. **네트워크 비용 최소화:** 백엔드와 직접 통신(1-Hop)하는 React 아키텍처가 프록시 레이어를 거치는 구조 대비 **네트워크 지연 시간을 약 3.5배 단축**합니다.
2. **클라이언트 자원 활용:** UI 렌더링 및 데이터 파싱 부하를 서버에서 클라이언트(브라우저)로 위임함으로써, 웹 서버의 CPU/메모리 부하를 방지하고 트래픽 확장(Scale-out)에 훨씬 유리한 구조를 갖춥니다.
3. **마이크로서비스(MSA) 적합성:** UI 서버와 API 서버의 역할을 완벽히 분리(Decoupling)하여, 장애 격리와 독립적 배포가 가능한 현대적 IT 서비스 요구사항에 완벽히 부합합니다.
